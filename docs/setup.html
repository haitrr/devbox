Working environment

Devbox: a containerized dev machine, driven remotely

A Docker container on the Mac that hosts every repo, every worktree, and every agent session — reached over SSH from Orca, VS Code, and the terminal. It is also the sandbox that makes running agents with approvals skipped a bounded risk. Compiles are shared and cached across worktrees. Rebuilding the image loses nothing.

The shape of it

Nothing of value lives in the image. The image is a toolchain; state lives on named volumes; work lives in ~/workspace. Clients attach from outside over one SSH port.

Why host keys are on a volume. Image-baked keys change on every rebuild, so the box looks like a different machine each time and strict clients (Orca, anything with a known_hosts) refuse to connect. They're generated once by the entrypoint into /etc/ssh/host-keys and kept.
Why sshd probes its clients. Sessions arrive through the host's port forward, and every NAT hop in that chain drops idle mappings after minutes — host sleep or Wi-Fi roaming drops them outright. sshd's default is to send nothing and let TCPKeepAlive handle dead peers, but that waits out the kernel's tcp_keepalive_time of 7200s, so a dead session sits wedged for up to two hours. ClientAliveInterval 15 with ClientAliveCountMax 8 holds the mapping open and reaps a silent peer in ~2 minutes. Long-running agent sessions are what suffer. Clients want the mirror image — ServerAliveInterval 15, ServerAliveCountMax 8 — so both ends notice.

Why a container: agents run with permissions skipped

Inside the box, Claude Code runs as claude --dangerously-skip-permissions — no per-tool approval prompt, which is what makes unattended and parallel agent runs practical at all. That is only a reasonable trade because the blast radius is bounded by the container rather than by my attention at each prompt. The list below is the actual boundary, in both directions.

Contained what a skipped-approval command cannot reach

  • The host filesystem. Exactly one path is mounted from the Mac — ~/.ssh/id_ed25519.pub, read-only. No source outside the box, no ~/.aws, no keychain, no browser profiles, no dotfiles.
  • My SSH identity. Only the public key crosses the boundary; the private key never enters the container.
  • Root. The dev user's sudo needs SUDO_PASSWORD, which is deliberately never written into any session file. With it unset the account is locked and sudo simply refuses — root work has to come from outside via docker exec -u root.
  • The Docker daemon. No /var/run/docker.sock mount, no privileged, no added capabilities — so there is no path back out to the host.
  • The host's processes, ports, and other containers, beyond what the network exposes to anyone.

Exposed the real blast radius

  • Everything in ~/workspace — every clone and worktree, including uncommitted work. The volume outlives the container, so docker compose down undoes nothing: an rm -rf in here is as permanent as it would be on the host.
  • GH_TOKEN — whatever push access that token carries. It lives in ~/.ssh/environment and ~/.config/devbox-env.sh, readable by the dev user, i.e. by the agent.
  • CLAUDE_CODE_OAUTH_TOKEN — the subscription itself.
  • The network. Egress is unrestricted: the whole internet, plus whatever the LAN and the host expose to the container.
  • Published ports. 2223 and 3000 bind on all interfaces, so the dev server is visible to the network, not just to localhost.
The hole in "the private key never enters the container": ForwardAgent yes. For the life of an ssh devbox session, the host's SSH agent is reachable from inside the box, and any process running as dev — including an agent with approvals skipped — can sign with my key. Git doesn't need it (that's what the GH_TOKEN credential helper is for), so dropping ForwardAgent is worth doing if unattended runs happen while I'm logged in.
The container protects the host, not the work. Nothing here recovers uncommitted changes from a worktree an agent trashed. That is what the one-worktree-per-session layout and frequent commits are for, not the container boundary.

What happens on docker compose up -d

Two scripts. Root does only what needs root; everything under /home/dev is done by the dev user itself, so no ownership ever has to be repaired.

entrypoint.sh root

Writes GitHub's host key to /etc/ssh/ssh_known_hosts. Generates the SSH host keys into the volume if absent. Sets the sudo password from SUDO_PASSWORD, or leaves the account locked.

→

/etc/profile.d/devbox-env.sh

Every CARGO_*, SCCACHE_*, RUSTC_WRAPPER exported for interactive login shells. Root-owned and world-readable — so no secret goes here.

→

user-setup.sh dev

Installs the host pubkey as authorized_keys. Writes ~/.ssh/environment (non-interactive sessions) and ~/.config/devbox-env.sh mode 600 for the tokens. Wires gh as git's credential helper.

→

sshd -D -e

Foreground, logging to the container. restart: unless-stopped keeps the box up across reboots.

Secrets & auth

GH_TOKENgh authenticates with no gh auth login; git SSH remotes are rewritten to HTTPS so unattended agents don't need a forwarded agent
CLAUDE_CODE_OAUTH_TOKENSubscription token from claude setup-token. Deliberately not ANTHROPIC_API_KEY — that would bill API credits instead of the plan
SUDO_PASSWORDUnset ⇒ sudo disabled entirely; root work goes through docker exec -u root devbox. A runaway process can't silently escalate
GITHUB_KNOWN_HOSTSPublic, so it's defaulted in the committed compose file — a fresh clone works without a .env
GIT_USER_NAME / GIT_USER_EMAILWritten to ~/.gitconfig on every start. Not a secret, but per-user, so it lives in .env rather than the committed compose file
Why ~/.gitconfig is not on a volume. It is derived state — the credential helper and the commit identity are both rewritten from the environment on every start, so .env stays the one place they are set. The cost of getting this wrong is quiet: a git config --global run by hand inside the box works until the next rebuild, and then every commit fails with Author identity unknown. Agents hit it hardest, since they get the error rather than a prompt.

Orca remote

Orca connects over the same devbox SSH host and pushes a remote component in, the same shape as VS Code's server. Three volumes keep it from re-uploading and from losing session state on every rebuild.

~/.orca-remote

The pushed relay binary, one directory per version (relay-0.1.0+<hash>). A detached node relay.js holds a unix socket and fans out to per-session shells.

~/.orca-relay

Runtime scaffolding: bin/, opencode-overlays/, and shell-ready/bash/rcfile — every Orca terminal is a bash --rcfile off that, which is how the box's env reaches Orca sessions.

~/.orca

sessions/ and agent-hooks/ — the durable per-session state. Mirrored on the host at ~/.orca and ~/orca/workspaces/<repo>/<name>.

Worktree naming. Orca names each workspace after a sea creature, and the box's worktrees carry those names straight through: oxygen-internal-axolotl, -butterfish, -cowfish. The suffix tells you which Orca session owns the tree.

Worktrees

One clone per repo, then a flat fan of sibling worktrees under ~/workspace — never nested inside the parent checkout. Each is a branch someone (me or an agent) is working on right now, and each carries its own ./target.

/home/dev/workspace/
├── oxygen-internal                 [main]                              ← primary clone
│   ├── oxygen-internal-axolotl     orca session
│   ├── oxygen-internal-butterfish  orca session
│   ├── oxygen-internal-cowfish     orca session
│   └── oxygen-internal.worktrees/
└── airlayer                        [feat/driver-contribution-sign]     ← primary clone

Indentation shows which clone a worktree belongs to; on disk they're all siblings in ~/workspace. The exception to the flat layout is <tree>/.claude/worktrees/<name> — Claude Code makes those for itself, nested inside whichever tree it was working in.

No shared CARGO_TARGET_DIR. A single shared target dir made every cargo invocation in the box serialize on cargo's per-target-dir build lock — "Blocking waiting for file lock on build directory" — which reads as a hang under agent/non-interactive runs. Each worktree gets its own ./target; sccache is what shares work between them, and it does so safely.

Cargo: the shim, sccache, and mold

sccache and CARGO_INCREMENTAL are mutually exclusive — sccache refuses to run as a rustc wrapper when incremental is on. But their value is temporally disjoint, so the shim at ~/.local/bin/cargo picks one per worktree per phase.

Cold first build in a fresh worktree

sccache pays off exactly once — it warms the whole dependency graph out of the global cache. Incremental would buy nothing here.

env RUSTC_WRAPPER=sccache \
    CARGO_INCREMENTAL=0 \
    ~/.cargo/bin/cargo "$@"

# on success:
touch ./target/.sccache-warmed

Warm every build after

Deps now live in ./target and cargo's fingerprint never re-invokes rustc for them, so sccache is dead weight. Incremental takes over for the edit-rebuild loop.

env -u RUSTC_WRAPPER \
    CARGO_INCREMENTAL=1 \
    ~/.cargo/bin/cargo "$@"

Knowing the sharp edges

  • Warm with cargo build, not cargo check. A cold check only produces dep .rmeta; the next build — now with sccache off — would have to codegen every dep from scratch. build seeds both.
  • One-time recompile at the flip. Turning incremental on changes local crates' rustc flags and invalidates their fingerprint. Deps are unaffected — they're never incremental.
  • Concurrency. Two builds racing in the same worktree before the sentinel is written invalidate each other's local fingerprints once. Wasteful, harmless.

Mountpoints are pre-created in the image, owned by dev. A named volume seeds itself from the image's content at that path including ownership. If the path is absent from the image, Docker creates it empty and root-owned — and the entrypoint would have to chown it on every start.

Day to day

Host

ssh devbox                       # in
docker compose up -d --build     # rebuild, keep all state
docker compose restart devbox    # re-run setup (rotated key/token)
docker exec -u root devbox bash  # root, when SUDO_PASSWORD is unset
docker logs -f devbox            # sshd + setup warnings

Inside the box

cd ~/workspace/<repo>
git worktree add ../<repo>-<name> -b <branch>
cargo build                      # cold once, then incremental
cargo nextest run                # routed by the shim too
sccache --show-stats
cargo clean                      # drops the sentinel → next build cold
Rotating a key or token is a docker compose up -d, never a rebuild: the host pubkey is re-read from the bind mount and the env files are rewritten from scratch on every start.
